# Test and Demo Readiness

## Pilot

Run one full session with a colleague who hasn't seen the design, on the test device, using the test script. Fix
everything that breaks or confuses before real participants. Pilots catch most prototype bugs.

## Entry links and resets

| Need | Setup |
|------|-------|
| Start each task on its own screen | One starting point (flow) per task with its own link |
| Reset between participants | Restart link; clear variables; log out of any accounts used |
| Hide tool UI | Presentation mode, hide hotspot hints (Figma: hotspot hints off), full screen |
| Mobile device | Mirror app installed and signed in; device on Do Not Disturb; screen lock off |

## Device and environment

- Test on the device class you design for; a phone prototype on a laptop screen changes behaviour.
- Performance: large prototypes load slowly; preload by opening every flow before the session.
- Offline fallback: export screens as images or a video of the flow, in case the link or network fails.
- Remote tests: share the link with view-only access; confirm participants can't see comments or other pages.

## Sharing and permissions

- Prototype link access: "anyone with the link" for participants, but limited to the prototype (no edit, no comments).
- Remove internal notes, names of real customers, and unreleased information not needed for the test.
- For stakeholder demos, a separate copy with presenter notes.

## During the session

- Note where the prototype, not the design, caused a problem (missing path, broken link); don't count it as a usability
  finding.
- When participants go off-path, use the overlay and redirect neutrally ("That part isn't built; what would you expect
  to find there?"); their expectation is the finding.
